## Not satisfied / needs a decision

- Two-stage/cluster sources are thin: only the multi-stage or multi-motor groups can back those prompts, so they carry 4 prompts each (2-3 of them multi) and single designs carry 3. More multi-stage sources are still needed (spec 8).
- `motor` targets hold the canonical pinned motor-DB designation (`sftgen.motors.resolve` with the .ork manufacturer hint; e.g. .ork 'I216-CL(I)' -> '636I216-14A', 'G54-RL' -> '159G54-12A'), while the prompt text keeps the hobbyist name (DB common name where it exists: 'I216', 'a Cesaroni G54', 'an AMW N4000'). `reference.motors_resolved` carries the same resolved entry per motor (null when absent from the DB).
- Fix prompts carry `{DESIGN_JSON}` and `{OBSERVED}` placeholders; the stage that injects the failing draft must also fill `{OBSERVED}` with that draft's simulated value, person-rounded (e.g. '0.6 cal', '9 m/s').
- Two-stage prompts that name per-stage classes ('an I booster and a G sustainer') can only be encoded as `stages` + `motor_class` max with the current TARGET_KEYS; per-stage class limits are not checkable.
- Drift and flight-time limits in recovery prompts use a rough descent model (drogue 25 m/s, main 5 m/s, x1.35-1.6 margin); they are feasible for a sensible dual-deploy/chute design but not proven by the reference sim.
- Reference motors missing from the pinned DB are substituted by the closest same-maker / same-diameter motor when a prompt would name them (AMW 'O3800' 98 mm -> 'BB-98-17500' / N4000). Designs whose reference motor is custom or has no same-maker substitute (KERON, GragasMAY24, Amalia, Team01, HyperTEK L540, ASAT M2544, NKJ E17, LFS L839, UBI fenix...) never get the motor named; their prompts use altitude, size and class limits only.
- Infeasible ceilings use a hand-set per-class single-stage altitude table (`CLASS_CEILING_M`) with a 4x margin; worth a sanity check by someone who knows the current class records.
- `missing_info` is populated on every row, not only the 10% missing-information prompts: it always lists important items the prompt leaves unstated (wind, rail length, landing limit, motor limit, size limit, recovery type). On `missing_info` rows the omission is deliberate and drives the stated-assumption behaviour; elsewhere it is descriptive metadata.
- 15 source files could not be resolved to a real `.ork` in `ork/` (see `groups.json` `ork_paths` = null); their references come from the old trace text and the `<design>` flight block only, so motor per-stage detail and stored-sim conditions may be missing there.
